# Decisions

Append-only log. Format: decision · why · consequence. Superseded entries stay, marked `Superseded by D-xx`.

### D-01 · Gemini-only stack (2026-11-14)
- **Decision:** all LLM, voice and embedding calls go to Google Gemini.
- **Why:** hackathon co-hosted by Google DeepMind; tier-3 hackathon key; one provider = less glue.
- **Consequence:** paid key only (no training on our data). The hackathon account is deleted after the event → keep a personal key as backup.

### D-02 · Agent harness: Vercel AI SDK 7, not Google ADK (2026-11-14)
- **Decision:** text agent with `ToolLoopAgent`; voice with `google.experimental_realtime()` + `experimental_useRealtime` (AI SDK 7). Google ADK / Agent Runtime only as production story.
- **Why:** our Live session runs **client-direct** from the extension with tools executed in the browser — exactly the AI SDK realtime pattern. ADK's live mode is server-owned (audio through our server, extra WS service) and strongest in Python; we are one TypeScript/Next.js stack. AI SDK still exposes Gemini-specific features (search, URL context, Interactions API, Live, embeddings).
- **Consequence:** keep tools and data sources behind interfaces so a later switch to ADK only touches the runtime. Fallback for Live: `live.connect` from `@google/genai`.

### D-03 · Chrome extension is the primary delivery (2026-11-14)
- **Decision:** Lotse ships as a Chrome extension (MV3). No change to customer apps (CORPUS stays untouched).
- **Why:** works on apps we can't modify; enables demo step 3 ("second app without setup"); companies can force-install via policy.
- **Consequence:** no app-internal identity/roles/feature knowledge from the page itself → solved by D-04/D-05. In-app SDK (script/npm) and repo-scanning PR wizard (PostHog-wizard style) are **Later**; MV3 forbids remote code, so a shared core would be a bundled package, not a hosted script.

### D-04 · App knowledge, users and roles live in the central dashboard (2026-11-14)
- **Decision:** each org maintains per app: allowed domains, feature list (route, click path, required role), later handbooks and training catalog.
- **Why:** the extension can't read app code; central config replaces the need for a code integration.
- **Consequence:** today feature lists are written by hand for the demo flows; later generated by a repo-scanning agent (R-ORG-4) or a crawler with one test account per role.

### D-05 · Users log into the extension with their org account (2026-11-14)
- **Decision:** extension login (demo: Supabase Auth test users; later Entra ID / managed Chrome profile). Role comes from the org membership.
- **Why:** gives identity, role and pseudonymization without touching the customer app.
- **Consequence:** never read the app's cookies or tokens.

### D-06 · Three components (2026-11-14)
- **Decision:** Extension (client capabilities) · Dashboard (org admin) · Runtime (agent, decision API, LLM calls, token minting). Dashboard + runtime in this Next.js app; extension as separate build in `extension/`.
- **Why:** clear ownership for the 4-person team; one deployable server.

### D-07 · Observation = semantic events + numbered snapshot; screenshots only as fallback (2026-11-14)
- **Status:** observation/screenshot policy superseded by D-23.
- **Decision:** the extension sends events (click/route/search/error/idle with element role + label) and builds a numbered snapshot of interactive elements. Gemini answers with an element number.
- **Why:** cheap, fast, privacy-friendlier, robust; screenshots are expensive and contain personal data.
- **Consequence:** PostHog is **not** the live source (ingest latency; e.g. EBV-Portal masks all text, so its events lack labels). Optional later: tap `posthog.on('eventCaptured')` in apps that already have PostHog.

### D-08 · Three-tier intervention decision (2026-11-14)
- **Decision:** browser rules → lite model ("intervene?") → main model (which element, which sentence).
- **Why:** most events never cost an LLM call; low latency; bounded spend.

### D-09 · Actions are DOM-based (2026-11-14)
- **Decision:** highlight/click by element number in the content script. No pixel-based computer use for the demo.
- **Why:** 20/20 reliability rule. (`gemini-2.5-computer-use-preview-10-2025` is available if ever needed.)

### D-10 · Voice: openWakeWord locally, then Gemini Live with ephemeral token (2026-11-14)
- **Decision:** wake word "Hey Lotse" detected locally with **openWakeWord** (ONNX in the offscreen document); then a short Gemini Live session per question, token minted by the runtime with locked config (model, prompt, role, tools). Hotkey (e.g. Alt+L) as fallback.
- **Why:** open source and free (vs. Porcupine licensing); no audio leaves the device before the trigger; no always-on streaming (cost, privacy, hackathon abuse rule).
- **Consequence:** custom "Hey Lotse" needs a trained model (see research). Mic permission must be granted once in a normal extension tab. Build order: hotkey → Live → highlight first, wake word on top.

### D-11 · UI surfaces (2026-11-14)
- **Decision:** overlays (frame, arrow, bubble, tour, status) in a Shadow DOM inside the page; side panel only for chat history; spoken answers shown as in-page subtitles.
- **Why:** side panel can't be opened programmatically by a wake word; Shadow DOM isolates styles both ways.

### D-12 · Privacy by design (2026-11-14)
- **Decision:** filter in the extension (labels yes, values/content no); pseudonymous user ids; admins see only aggregates (min. group 5); visible "Lotse aktiv" indicator.
- **Why:** employee monitoring needs works-council codetermination (§ 87 (1) 6 BetrVG); EBV data includes Art. 9 GDPR categories. Pitch line: "we find weak spots in the UI, not in people".

### D-13 · Two kinds of insights (2026-11-14)
- **Decision:** dashboard shows (a) training suggestions for people and (b) UX optimization potential for the app.

### D-14 · Monorepo with npm workspaces (2026-11-14)
- **Decision:** three apps + one contract package: `apps/extension` (WXT 0.21, Chrome MV3), `apps/server` (Next.js, :3001, runtime), `apps/dashboard` (Next.js, :3000, org admin), `packages/shared` (zod schemas + types, TS source). One `.env.local` at the repo root for all apps; Supabase stays at root `supabase/`. Refines D-06 (dashboard and runtime are now separate apps).
- **Why:** three people work in parallel on technically separate, independently runnable parts; WXT gives MV3 bundling, HMR and manifest generation with little setup.
- **Consequence:** apps talk only via HTTP + `@lotse/shared`; root scripts `dev:server` / `dev:dashboard` / `dev:extension`; `build`/`lint`/`typecheck` run across workspaces; `db:types` writes `packages/shared/src/database.types.ts`.

### D-15 · Area ownership and boundaries (2026-11-14)
- **Decision:**
  - Extension dev owns `apps/extension` — talks to the server via HTTP (`/api/lotse/*`, only from the service worker).
  - Server dev owns `apps/server` — **all Gemini/embedding calls**, event/hint tables; reads org/knowledge tables.
  - Dashboard colleague owns `apps/dashboard` — org creation, onboarding of organizations, central knowledge base, user management; owns migrations for orgs/members/apps/app_features/knowledge tables; embeds knowledge via a server endpoint (planned `POST /api/knowledge/ingest`).
  - Everyone owns `packages/shared` + `supabase/migrations` — change via small PR and tell the others.
- **Why:** avoid merge conflicts; one place for keys and LLM spend.
- **Consequence:** don't edit another area's folder without telling its owner; contract changes go into `packages/shared` first; schema only via new migrations, never edit merged ones; no Gemini key outside the server.

### D-16 · One brain on the server; voice is only input/output (2026-11-14) — refines D-10
- **Decision:** wake word (openWakeWord) or hotkey Alt+L → offscreen document transcribes (Gemini Live transcription via ephemeral token from `POST /api/lotse/live-token`; fallback Web Speech API) → text goes to the central agent `/api/lotse/ask` (`source: "voice"`) → only a `say` event is spoken (`chrome.tts`). No conversational Live agent.
- **Why:** the user wants the agent centrally on our server, and **no talking when a marker answers the question** — only controllable if our runtime decides what is said.
- **Consequence:** audio still goes browser → Gemini directly (never through our server); same tiers, limits and tracking for voice and text.

### D-17 · Show only, never act (2026-11-14) — supersedes D-09 and R-ACT-1/2
- **Decision:** Lotse marks fields/elements (agent cursor + highlight + short hint) and lays out multi-step plans; it never clicks or fills anything. No `clickElement` tool.
- **Why:** goal is to train employees; differentiator vs. acting browser agents (see research → Competitors).

### D-18 · Model tiers chosen by an orchestrator in the runtime (2026-11-14)
- **Decision:** `point` (target on current page, one marker, fast model, minimal thinking) · `guide` (multi-step/off-page, tools: feature list + knowledge search, `showPlan`) · `reason` (ambiguous/analysis, smart model). Heuristic routing first, lite-model classification only when unsure. Proactive "intervene?" via a lite model on `/api/lotse/decide`.
- **Why:** most questions are simple "where do I click" → fast and cheap; hard ones get more steps/thinking.

### D-19 · Guidance as an NDJSON event stream (2026-11-14)
- **Decision:** `POST /api/lotse/ask` streams `GuidanceEvent`s (`tier`, `point`, `plan`, `say`, `done`, `error`; schema in `@lotse/shared`). UI tools emit their event the moment the tool call arrives. Multi-step plans advance **locally** in the extension (label match in a fresh snapshot after each click/navigation) — no server call per step.
- **Why:** first highlight on screen before the agent finishes; framework-agnostic for a service-worker client.

### D-20 · Local prefilter + rules; server only on demand (2026-11-14)
- **Decision:** the extension keeps only semantic events (no values, no mousemove/scroll), runs the stuck rules locally and calls `/decide` only when a rule fires; analytics go in batches (≤ 100, ~30 s) to `/api/lotse/events`. Proactive help is a user setting (`proactive`, default on) with cooldown (1 offer / 2 min, "Nein" → 10 min snooze).
- **Why:** data volume, cost, privacy; proactive offers can be annoying.

### D-21 · Runtime safety: auth, limits, tracking (2026-11-14)
- **Decision:** Supabase access token (dev: anonymous per session id); per-session rate limits and daily token budget; per-tier timeouts and max output tokens; kill switch `LOTSE_DISABLED`; every LLM call logged to `agent_usage`; page labels treated as untrusted data (prompt-injection).

### D-22 · Decisions API + adaptive per-user threshold for proactive help (2026-11-14)
- **Decision:** `/api/lotse/decide` uses Google's Decisions API (`gemini-decision-1`, available for our key) — Boolean "needs help?" with calibrated confidence + Choice over the app's feature names, one call; offer text from a template. Lotse intervenes only if yes AND confidence ≥ the user's threshold. Threshold starts at 0.80 (range 0.60–0.95, constants `PROACTIVE_THRESHOLD` in `@lotse/shared`): 👎 +0.05, 👍 −0.02, "Nein" +0.02; manual override via `PUT /api/lotse/prefs`.
- **Why:** proactive offers are only good if they rarely annoy; calibrated confidence makes the cut-off meaningful, feedback personalizes it.
- **Consequence:** feedback per offer is stored (pseudonymous) → aggregated "helpful offers per feature" for the dashboard; the per-user threshold is personal and never shown to admins.

### D-23 · Separate observability inferences and local visual history (2026-11-14)
- **Decision:** follow the user's explicitly reconfirmed order: events/DOM to UI-state inference (`/state`), local chronological inferred-state/action buffer, workflow/intent inference (`/intent`), separate intervention decision (`/decide`), then actual guidance (`/ask`). State/intent/decision receive no screenshots. Selected local historical frames are attached only after a positive intervention decision or for an explicit question.
- **Why:** the user wants explicit state, workflow and intent understanding with visual history available for actual help.
- **Consequence:** refines D-08 and supersedes D-07's earlier screenshot policy and D-20's gate that waits for a rule before model calls. Local rules annotate the decision input; `workflow_update` allows inference without a rule. The extension retains bounded local history and validates snapshot IDs. Explicit questions bypass state/intent/decision and use existing context. Gemini endpoints remain user-owned; extension implementation and shared contracts are handed off in `docs/handoff-extension.md`.

### D-24 · User's delivery and validation instructions (2026-11-14)
- **Decision:** work on main and push directly; no pull requests or tests (including browser/AI smoke tests). Static typecheck, lint and extension builds validate this task.
- **Why:** explicit standing user instruction.
- **Consequence:** overrides D-15's PR workflow and older validation guidance. Existing teammate smoke scripts are preserved but not run. No claim of 20/20 demo reliability; the handoff records remaining runtime/voice/plan integration.

### D-25 · One-time exploration by an admin, then continuous learning with approval (2026-11-14)
- **Decision:** an org admin starts an **exploration** once per app (test account + test data): the extension visits every page of the app, opens menus/tabs/dialogs and records a page map (routes, elements, click paths, per-element style metrics). `POST /api/lotse/explore` turns it into feature suggestions (`FeatureSchema`) and design findings (rules: contrast, target size, unlabeled icon buttons, duplicate labels, click depth > 4, overloaded pages, dead ends; Gemini only summarizes). After that, `POST /api/lotse/learn` (button "Jetzt auswerten" + every 10 min while the server runs) finds unknown features, stale click paths, agent errors (agent_usage errors/timeouts, 👎) and knowledge gaps, and refreshes `insights`. Everything lands in `lotse_suggestions`; nothing changes app knowledge without an admin clicking "Übernehmen".
- **Why:** "Einrichtung in 60 Sekunden statt Touren in Wochen", and the system keeps improving (user, 2026-11-14).
- **Consequence:** the exploration is the only place where Lotse clicks — refines D-17 for setup mode only: admins only, navigation only (links, tabs, menus, open dialogs; close via Escape/"Abbrechen"), never submits forms, never clicks delete/remove/send/save/submit/confirm/pay/logout or red/danger buttons, same origin, page and time limits, visible progress + stop. Employees never trigger it.

### D-26 · Pseudonymize in the browser before anything leaves it (2026-11-14)
- **Decision:** the extension replaces personal data with stable per-session placeholders before sending events, questions, snapshots or frames: content strings of the page (table cells, record headings, card titles — not UI labels) and patterns (IBAN, e-mail, phone, "Herr/Frau <Name>", street + number) become `[Kunde-1]`, `[Person-2]`, `[IBAN-1]`, `[E-Mail-1]` … (`PSEUDONYM_TOKEN` in `@lotse/shared`). The mapping stays in the browser; answers are shown with the real names again. Frames: content regions are painted over before upload.
- **Why:** "nicht mehr Herr Müller sondern Herr A1" (user, 2026-11-14) — server and Gemini only ever see placeholders.
- **Consequence:** pseudonymized, not anonymous (a freely typed name not on the page is only caught by patterns). Server prompts treat `[…-n]` tokens as opaque ids and never ask for the real value.

### D-27 · Server-side app policy with blocked routes; extension login (2026-11-14) — implements D-05, hardens D-12
- **Decision:** the runtime decides per app host whether Lotse may run and where it must stay silent: `GET /api/lotse/policy?app=<host>` → `allowed`, `blockedRoutes`, app/org name and (signed in) the caller's org role. CORPUS hosts always get the fleet patterns `*fahrzeug*`, `*vehicle*`, `*fleet*`, `*fuhrpark*` (env `LOTSE_CORPUS_HOSTS`, `LOTSE_FLEET_ROUTES`, per app `LOTSE_BLOCKED_ROUTES`); unknown hosts are allowed in dev only. The extension enforces it **fail closed**: unknown policy or a matching location (path + query + hash, checked locally) → no DOM reading, no events, no snapshots, no screenshots, no inference, no questions — even while recording — and "Lotse pausiert auf dieser Seite" in overlay and side panel. Extension login: Supabase email/password in the side panel, session in `chrome.storage.session`, `Authorization: Bearer` on every runtime call (refresh + one retry on 401); without login the dev mode with the manual demo role keeps working.
- **Why:** "Die Fahrzeugseiten bleiben außen vor, weil dort der echte Fuhrpark steht." — the hard demo rule must not depend on the presenter remembering to pause; identity and role should come from the org, not a text field.
- **Consequence:** blocked patterns live in server env today; a dashboard-managed per-app blocklist (column on `apps`, owned by the dashboard) is the natural next step. The exploration crawler (D-25) and any future capture path must apply the same policy (never navigate into or record blocked routes). The manual demo role is no authorization boundary; in production the server ignores it for members and refuses unknown apps.

### D-28 · Agent memory: Lotse learns incrementally from usage — labeled, k-anonymous, admin-controllable (2026-11-14) — refines D-25
- **Decision:** next to the curated knowledge base (`documents`, written by admins) Lotse keeps a separate, clearly labeled **agent memory** (`agent_memory`; kinds `faq` · `role_hint` · `pitfall` · `path_hint` · `gap_resolution`; source `agent` · `learn_loop` · `admin`). The model has **no memory tool**. After each explicit `/ask` the server maps the question to a neutral topic (lite model, reusing known topics so phrasings cluster; the question itself is never stored) and records evidence per hashed pseudonymous person: unanswered (no point/plan, or knowledge search without hits) → `knowledge_gaps`; answered → `faq` ("„IBAN ändern“ meint „Bankverbindung ändern“"); role-blocked → `role_hint`. A memory starts `proposed` and becomes `active` only with ≥ 5 distinct persons and no 👎 (k-anonymity) — or when an org admin writes/approves it (`/api/lotse/memory`; answering a gap creates an active `gap_resolution`). 2 × 👎 on offers for that feature demote it; 60 days without new evidence → `expired`. Active memories reach `/ask` as an `<agent_memory>` block (≤ 6, ≤ 1 200 chars, "learned, lower priority than features"), `/decide` as `learned` hints, and the agent's `searchKnowledge` via embeddings.
- **Why:** "…dass der Agent in der Wissensbasis etwas speichern kann, das aber klar als Agent Memory oder sowas gekennzeichnet ist, dass man inkrementell über Wochen oder Monate hinweg Nutzerverhalten lernt und so den Agent und die Vorschläge optimieren kann." (user, 2026-11-14)
- **Consequence:** page content can at most shape a proposal (through a sanitized topic label), never activate one; promotion runs in SQL (`record_agent_memory_evidence`), so concurrent evidence can't skip the threshold. Admins see memories and gaps only aggregated (gaps ≥ 5 persons). One extra lite-model call per explicit question runs after the answer (logged as `agent_usage.route = 'memory'`, `LOTSE_MEMORY=0` turns it off). The learn loop (D-25) proposes `pitfall`/`path_hint` memories with its subject lists and turns gaps into `knowledge_gap` suggestions (`docs/notes/reply-ismail-learning-loop.md`).

### D-29 · Always-on status orb and auto-activation on the org's app domains (2026-11-14) — refines D-11, D-12, D-27
- **Decision:** (1) **Auto-activation:** once signed in, Lotse observes by itself on every app of the user's org — no "Start" click. The policy gains `autoStart` (allowed and the caller is a member of the app's org; in dev also apps the runtime knows: dashboard row or bundled fixture, e.g. the demo CRM) and `appDomains` (signed in: all `apps.domains` of the caller's orgs). The service worker (`utils/activation.ts`) follows the focused tab: app page + route not blocked → `start()`; the tab it started leaves the org's apps → `stop()`; blocked route → no start (resumes on an allowed page). A manual pause (orb menu or side panel) holds until the user resumes and survives page loads (`chrome.storage.session`). Switch "Automatisch aktiv" (default on). (2) **Status orb:** a 48 px circle on org app pages (`utils/orb/`, own Shadow DOM, `popover="manual"` in the top layer, re-parented into open modal `<dialog>`s), draggable with the position stored per host. It shows not connected, not signed in, active, paused (user), paused (blocked route / app not allowed), listening (pulsing ring — pushed on the wake word / hotkey), thinking, speaking, offer, error — colour + icon + animation + tooltip + `aria-live` text. Click = push-to-talk (`startListening`); menu (right click, long press, "⋯", Shift+F10) = pause/resume, ask, open side panel (Alt+L hint when Chrome refuses), hide on this site. Switch "Status-Kreis anzeigen" (default on); it replaces the overlay's status chips while visible.
- **Why:** "…wenn man sich einmal angemeldet hat, den Lotsen nicht nochmal manuell aktivieren muss, sondern er automatisch dauerhaft aktiv ist, sobald diese spezielle Domain … aufgerufen wird" and "ein Overlay UI-Element in Form eines Kreises … soll … den Status des Lotsen anzeigen … bei Default immer angezeigt werden und auch direkt auf den Voice-Cue reagieren" (user, 2026-11-14). The orb is also D-12's visible "Lotse aktiv" indicator.
- **Consequence:** auto-start never weakens D-27 — the same fail-closed policy gates every start, and an unknown or unreachable policy means no start (orb: "nicht verbunden"). The content script and `activeAppTab()` are still localhost-only; real org domains need optional host permissions + dynamically registered content scripts (README). The orb polls the worker every 1.5 s while visible; voice state is pushed.

### D-30 · Explicit trigger: repeated clicks on the same spot (2026-11-14)
- **Decision:** ≥ 5 presses on the same element (role + label + route; else the same 24-px screen cell) within 20 s emit a `repeated_click` event (detail `clicks=n;disabled=true|false;reason=<tooltip>`), captured via `pointerdown` because Chrome fires no click on disabled controls. It is the highest-priority local rule; `/decide` treats it as strong evidence (P ≥ 0.9, the user's adaptive threshold still applies) and offers "„X“ ist gerade gesperrt – soll ich dir zeigen, warum?". `/ask` sees disabled elements as "(deaktiviert)" and points at what unlocks them.
- **Why:** users press disabled buttons that "do nothing" and don't understand why (user, 2026-11-14).

### D-31 · Dashboard follows the Valo design handoff; product name centrally swappable (2026-11-14)
- **Decision:** the dashboard implements the "Valo – Admin-Dashboard" design handoff: IBM Plex Sans/Mono, navy/petrol tokens as a Tailwind v4 `@theme` block (`apps/dashboard/src/app/globals.css`), light only for now (dark tokens kept, opt-in via `data-theme="dark"`; the user wants the content panel white), shell header with pill navigation, sidebar ("Erkenntnisse nach App", quick actions, privacy box), sand-white panel; UI building blocks in `apps/dashboard/src/components/ui.tsx`. Routes are German like the design (`/anmelden`, `/registrieren`, `/erkenntnisse`, `/schulungen`; old English routes redirect, `/lernen` stays because the extension links to it). The visible product name is `PRODUCT_NAME` in `ui.tsx` (currently "Valo").
- **Why:** the user handed over a high-fidelity design for the admin dashboard ("Setze dieses Design schema um für das Dashboard") and doesn't like the working name "Lotse".
- **Consequence:** server, extension and package names still say Lotse; renaming them is a separate step for their owners. Only layout A of the insights page (cards per app) is built; layouts B/C of the handoff were alternatives.

### D-32 · Product name is Valo everywhere users see it; internal names keep "lotse" (2026-11-14) — completes D-31
- **Decision:** every user-, admin- and juror-facing text says **Valo**: extension manifest (name, description, action title, command descriptions), side panel, status orb, overlay, offer/status/error and voice texts, mic-permission page, toolbar icons (16/32/48/128 px rendered from the dashboard's lighthouse logo into `apps/extension/public/icon/`), the agent persona and all stage prompts (ask/decide/state/intent/explore), server status page, live-transcription vocabulary ("Valo", "Hey Valo"), and the prose of README, SETUP, AGENTS, `docs/`, RUNTIME/VOICE docs and demo-CRM docs. Extension commands also get macOS keys: `lotse-ask` ⌘⇧L, `lotse-listen` ⌘⇧K (Alt+L / Alt+Shift+L elsewhere; UI hints pick the label per platform).
- **Why:** "Ändere das komplette Branding auf Valo." (user, 2026-11-14) — the dashboard already said Valo (D-31) while extension and runtime still said Lotse. Shift on macOS because plain ⌘+letter is taken by Chrome or by web apps (⌘K = the demo CRM's command palette).
- **Consequence:** internal identifiers intentionally keep "lotse" — renaming them would break the running system and teammates' code: npm packages `@lotse/*` and workspace scripts, env vars `LOTSE_*`, headers `x-lotse-*`, API paths `/api/lotse/*`, tables/columns `lotse_*` and migrations, `chrome.storage` keys and message types `lotse:*`, file/folder names, code identifiers (`LotseEvent`, …). Older decisions above keep the old name. The wake word stays "Hey Jarvis": no pre-trained "Hey Valo" openWakeWord model exists, a custom model would have to be trained (the transcript strip already accepts "Valo"). Chrome applies new suggested shortcuts only on a fresh install — existing installs keep their binding until the extension is removed and loaded again or rebound at `chrome://extensions/shortcuts`.

### D-33 · Data access and deletion per person (2026-11-14)
- **Decision:** `GET /api/lotse/me` (signed-in only, else 401) returns row counts per table + the person's own stored proactive threshold (`MyData`), never contents, hashes or other people's data. `DELETE /api/lotse/me` deletes the person's rows in the 7 runtime tables — `agent_usage`, `lotse_events` (`user_id`), `lotse_user_prefs`, `lotse_offers`, `lotse_offer_feedback` (`subject_id = u:<sub>`), `agent_memory_evidence`, `knowledge_gap_subjects` (`subjectHash(u:<sub>)`) — then recounts `agent_memory.persons/negatives` and `knowledge_gaps.persons` from the remaining evidence. `DELETE ?userId=<uuid>` lets an org admin delete a member of an org they administer (else 403). Own low rate limit (`me`, 6/min). A failing table aborts with 500 and names the tables already deleted.
- **Stays on purpose:** data from before login (`s:<session>`) can't be attributed to a person; `agent_memory` / `knowledge_gaps` entries themselves stay (only their counters drop; below 5 persons they are invisible to admins anyway, D-28); memory `status` and `evidence_count` are not re-evaluated (next learning run / new evidence does). Recount is not atomic (no SQL function = no migration); concurrent evidence during a delete may be off by one until the next write.
- **Why:** GDPR access/erasure per person and works-council trust (D-12).

### D-34 · English-first product UI; agent answers in the user's language (2026-11-14)
- **Decision:** English-first product UI; agent answers in the user's language, English fallback; customer app data/labels untranslated. The runtime server (`apps/server`) returns every user- and admin-facing text in English: error messages of all `/api/**` routes, proactive offer and intent templates (`/decide`, e.g. "Want me to show you where to find “X”?"), learn/design/memory/gap/insight texts for the dashboard, playground and status page. Gemini prompts whose output admins see (insights, knowledge-gap topics, UI-state and intent stages) ask for English; the explore stage names features in the app's own language. The `/ask` agent answers in the language of the question and falls back to English when unsure (was German), addresses the user informally and never translates page labels or feature names. TTS picks en-US on ties (German only with clear evidence); one English style instruction for all voices.
- **Why:** "Die komplette App muss auf Englisch sein, nicht auf Deutsch." (user, 2026-11-14).
- **Consequence:** customer app content stays as it is (German demo CRM labels, feature names, fixtures, seeds, pseudonym kinds like `[Kunde-1]`, click-path placeholders like `<Kundenname>`); enum values in contracts (`schulung`, `hoch`/`mittel`/`niedrig`) and internal `lotse` names are unchanged. Rows written before this change (e.g. German topics, memory texts, the old "Fragen allgemein" insight label) keep their German text until they are refreshed. German keyword matchers (tier cues, stop words, close/generic labels) stay so German questions keep working.

### D-35 · Trainings come from employee questions; backing visible to all org members (2026-11-14)

### D-36 · DB guard: an org always keeps at least one admin (2026-11-14)
- **Decision:** migration `last_admin_guard` adds a `BEFORE UPDATE OR DELETE` row trigger on `public.org_members` (`guard_last_org_admin`, security definer). Demoting, deleting or moving an admin to another org raises `An organization needs at least one admin (last admin).` (`P0001`) when no other admin is left in that org. Cascades pass: if the parent org or auth user row is already gone (FK cascades run after the parent delete, so the trigger no longer sees it), the trigger allows the delete. A per-org `pg_advisory_xact_lock` serializes the checks, so two admins demoting each other at once can't both succeed (READ COMMITTED).
- **Why:** before, only the dashboard blocked self-demotion; RLS "admins manage members" let any admin demote or remove every admin through the API, which could lock an org out of its own dashboard.
- **Consequence:** the dashboard should show the error message when it gets one. Deleting the last admin's auth account still goes through (account deletion must not be blocked) and leaves the org without an admin, so a service-role fix is needed then. One statement that demotes all admins fails as a whole.

### D-37 · Admin data delete from /team only for single-org members (2026-11-14)

### D-38 · Own wake word "Hey Valo" / "Hey Daddy"; "Hey Jarvis" stays as fallback (2026-11-14)

- **Why:** user asked for "Hey Valo" and "Hey Daddy" as wake words (2026-11-14); no pre-trained model exists for either.
- **How it was trained:** synthetic speech only — 30 Gemini TTS voices + 33 local macOS voices (de/en), augmented (speed, reverb, band-limit, noise, babble), features computed exactly like `wakeword.ts` (streaming mel → embedding), small MLP head, exported to ONNX. Held-out voices: 94 % of wake word clips detected, 0 of 114 office/pitch sentences fired, 7 % of near misses ("Hey Danny") fired.
